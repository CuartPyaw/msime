# Agent Note: Windows 日语切回中文后立即发布方案

Status: implemented

## Problem

Windows 的 `Ctrl+Shift+J` 日中切换先在独立工作线程写入共享偏好，再由 `PreferenceMonitor` 每 250 毫秒轮询并发布给输入会话。用户从日语切回中文或英文后马上继续输入时，当前会话仍可能沿用日语方案，于是新字符继续变成假名。方案文件已经写成功，但生效时序落后于用户的下一次按键。

## Decision

日语切换工作线程成功写入方案后，唤醒 Windows 的 `PreferenceMonitor`；监视器仍负责读取带版本的完整快照、排入输入队列并按原有顺序发布，不绕过版本检查或在工作线程直接改 Engine。`wake()` 在同一互斥量下记录待检查状态，再通知条件变量；每轮开始消费这个状态，处理期间到达的通知留到下一轮。等待谓词同时检查停止和待检查状态，不能只通知而让谓词继续等待原截止时间。

只有输入队列回执尚待确认时以 10 毫秒短轮询推进，空闲仍使用原有 250 毫秒间隔；否则新快照已应用，广播回调还会再晚一个空闲周期。队列任务仍只捕获快照值，停止不等待回执，也不把监听器指针交给晚到任务。

Server 构造期间已经可能接收快捷键，唤醒回调的安装、调用和撤销共用互斥量。构造返回后立即建立撤销守卫，再安装回调并补查一次偏好；任何后续构造抛异常时，守卫先等待旧调用结束并清空回调，随后才析构 Server。托盘偏好锁在通知前释放，避免与监听器广播反向持锁。

## Alternatives considered

- **让切换工作线程直接修改活动会话**：需要把完整偏好快照和焦点租约跨线程传回输入队列，容易绕过已有的 revision、组字延迟和会话失效检查，因此不采用。
- **把轮询间隔永久缩短**：会增加无变化时的磁盘读取和锁竞争，仍不能表达“写入完成后立即检查”，因此不采用。

## Consequences

这项修复缩短 Server 偏好发布延迟，保留组字期间的延迟应用与停止语义。它不建立 `NoReply` 后下一键的顺序屏障；TIP 的本地 `HostEngineAdapter` 仍由独立的 500 毫秒定时器异步刷新，`InputModeChanged` 只更新全局方案标记与图标。#9431 继续跟踪完整切换协议和真实编辑器验收，本次使用 `Refs`。

验证包含一分钟空闲间隔下的显式唤醒发布回归；另用真实 `PreferenceMonitor.cpp/.h` 编译线程探针，旧实现确认已等待后发通知，300 毫秒内读取次数不变而失败；修复后约 12 毫秒发布新修订。输入队列与偏好存储在该探针中是合成依赖，不能代替生产链。

原提交的 GNU job 完成交叉构建但明确未执行 Windows 程序；原生 Windows job 只验证设置 UI，未执行这里的监控器回归或生产 TIP/Server 联调。新增完整 quick、永久回归及最终提交 CI 的结果分别记录，不能把编译称为输入链验收。

最终增量的完整 `verify-local.sh --quick` 在限制契约与 Rust 并发为 2 后退出 0（`resumed-quick-warm.log`），本机原生测试 164 项通过。首轮两个未改动门禁分别在 Swift 与 Rust 编译达到 120 秒超时，原命令单独复验均通过；重跑没有改超时、失败基线或断言。便携唤醒、停止与停止后通知回归也重新通过。完整 Windows 宿主与 pipe-only 编译因未安装 MinGW、未配置 `target/win-full` 被明确跳过，真实 Windows `InputQueue` 用例和 TIP/Server 联调仍待补齐。
