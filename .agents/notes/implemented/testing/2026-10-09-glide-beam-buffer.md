# Agent Note: 滑行解码 beam 缓冲复用

Status: implemented

## Problem

滑行解码在每一轮 beam 扩展时为每个候选前缀重新分配字母、音节树状态和采样点代价向量；`prune` 还会为每个采样点及每个前缀创建临时嵌套向量。长笔画会生成数万条短命前缀，这些分配占据了解码路径的大部分开销。既有的滑行输入行为和宿主契约见[滑行输入的引擎解码与宿主契约](../feature/2026-10-07-glide-typing-engine.md)。

## Decision

`Decoder::run` 维护一个可回收的前缀缓冲池。每个新候选从池中取出 `Prefix`，清空并复用其中的 `letters`、`states` 和 `costs` 容器；被 beam 剪枝或最终上限过滤掉的前缀回收到池中，下一轮继续使用。`prune` 额外接收跨轮次复用的采样点 token 列表和保留标记，避免每轮重建嵌套向量。候选顺序、成本比较、beam 上限、音节状态和最终回溯保持原算法语义。

分配回归测试以 29 字母长笔画覆盖真实 beam 形状，要求完整 `decode_glide` 调用不超过 22,000 次分配；旧实现约 160,000 次，新实现约 20,000 次。

## Alternatives considered

- **只复用 `prune` 的临时向量**：能消除每轮采样点和保留标记的分配，但每条前缀仍会重复分配三个内部容器，长笔画的主要开销仍然存在。
- **给每个前缀改用固定大小数组**：可以把短状态放到栈上，但会把最长字母串和所有代价条目的容量固化在结构中，增加每个 beam 节点的复制体积，也不适合代价条目数量随采样点变化的路径。
- **只预留 `Vec` 容量而继续创建新前缀**：可以减少扩容次数，却无法复用已被丢弃前缀的内部缓冲，仍会为每个候选建立新的堆对象。

## Consequences

长笔画解码的临时堆分配显著减少，beam 搜索仍保留动态长度和既有剪枝规则；缓冲池会在一次解码期间持有达到峰值的前缀容量，换取后续轮次不再反复申请和释放。新增测试同时覆盖真实入口与分配预算，既有几何、词典排序和会话行为测试继续验证输出语义。
